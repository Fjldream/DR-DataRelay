# TCP 数据转存工具需求分析

## 1 文档目的

本文档用于明确现场低功耗水表及流量计数据从 TCP 报文接入、解析、缓存并通过 KingHistorian RESTful 接口写入 KH 3.52 的完整需求，作为后续协议确认、技术设计、开发、联调和验收的基线。

当前结论是：原方案中的 MQTT Broker、MQTT Topic 和 KIO 3.8 不再属于新链路。现场设备可配置目标服务器 IP 和端口，由设备主动建立 TCP 连接并直接发送原始文本报文。Node.js 服务只接收报文，不向设备发送应用层心跳或 ACK。

## 2 需求来源和已确认信息

### 2.1 已阅读材料

- `source/MQTT数据转存需求_副本.docx`：说明原业务目标、设备规模、历史数据批量上传示例及最终在 KS 中查看趋势和报表的诉求。
- `source/现场部署架构与MQTT通信协议说明文档_副本.docx`：包含原 MQTT 链路、原始设备报文示例及字段含义。
- `source/KingHistorian_Restful接口_使用说明.docx`：说明 FDBServer 配置、客户端注册、变量创建、数据写入、错误返回和 HTTPS 配置。
- 客户提供的最新报文截图：确认 TCP 直接上传的原始报文格式。

### 2.2 已确认需求

1. 现场设备数量为 30 台以上，后续可能扩容。
2. 每台设备可配置目标服务器 IP 和 TCP 端口，并主动连接服务器。
3. 设备直接发送原始报文，不经过 MQTT Broker，不使用 MQTT Topic，也不需要 KIO 3.8 做中转解析。
4. 服务端使用 Node.js 实现 TCP 接入和业务处理。
5. 服务端不向设备发送应用层心跳、不发送 ACK，也不设计请求响应式交互。
6. 服务端将报文解析为 KH 点值，通过 FDBServer 提供的 RESTful 接口写入 KH 3.52。
7. 最终用户需要在 KS 中查询历史趋势和生成报表。
8. KH 数据写入接口为 `POST /api/v1/khinsert`，请求需要 `Authorization` 和已注册的 `clientName` 请求头。

## 3 新旧方案边界

### 3.1 新链路

```text
现场设备
  -> 主动建立 TCP 连接
  -> Node.js TCP 接入服务
  -> 报文分帧与协议解析
  -> 本地持久化队列
  -> KH RESTful 适配器
  -> FDBServer
  -> KH 3.52
  -> KS 趋势和报表
```

### 3.2 不再适用的原方案内容

- 厂商云服务器转发。
- MQTT Broker 和 MQTT Client。
- 通过 Topic 识别设备。
- 将多条记录包装为 `{ "DATA": [...] }` 的 MQTT JSON Payload。
- MQTT QoS、订阅恢复、Topic 权限等机制。

原文档中的设备字段定义、历史时间语义、KH RESTful 接口和最终展示目标仍然适用。

## 5 TCP 接入协议分析

### 5.1 报文示例

```text
@LEN:0212;STC:211000000800;SN:0000000000;IMEI:869098047062173;CIMI:460113126383366;CCID:89861120236017175088;TM:20210715153716;V:3.60;D:120;T:01;C:18;A01:3.066;A02:3.652;A03:0.036;P01:000003663;P02:000000054;K01:00;0B#
```

### 5.2 已知帧结构

| 项目 | 规则 | 当前状态 |
| --- | --- | --- |
| 编码 | 报文由英文字母、数字及 ASCII 标点组成 | 暂按 ASCII/UTF-8 兼容处理 |
| 帧头 | `@` | 已确认 |
| 字段分隔符 | `;` | 已确认 |
| 键值分隔符 | `:` | 已确认 |
| 帧尾 | `#` | 已确认 |
| 长度字段 | `LEN:0212`，固定 4 位十进制示例 | 长度计算口径待确认 |
| 校验位 | 最后一个分号后、`#` 前的两位值，例如 `0B` | 校验算法待确认 |
| 字段顺序 | 示例中顺序固定 | 服务端应按字段名解析，不应只依赖位置 |
| 大小写 | 示例为大写字段名 | 建议严格大写，是否兼容小写待确认 |

### 5.3 TCP 分帧规则

TCP 是字节流，单次 `data` 事件不等于一条完整报文。服务端必须为每个连接维护独立接收缓冲区，并执行以下规则：

1. 在缓冲区中寻找帧头 `@`，帧头前的无效字节记录后丢弃。
2. 从帧头开始寻找第一个帧尾 `#`。
3. 未找到帧尾时继续缓存，不进行解析。
4. 找到完整 `@...#` 后截取一帧，剩余字节继续循环解析，以支持粘包。
5. 一条报文被拆成任意多个 TCP 包时，必须只解析一次。
6. 同一次接收中包含多条连续报文时，必须逐条解析。
7. 超过最大帧长度仍未出现 `#` 时，判定为异常帧，清理至下一个 `@`，防止内存持续增长。
8. 连接断开时，如缓冲区仍有不完整帧，保存异常记录但不写入 KH。

建议最大原始帧长度默认设为 4 KiB，并允许配置。最终值应根据厂商协议的最大字段数确定。

### 5.4 连接行为

- 设备作为 TCP Client，Node.js 服务作为 TCP Server。
- 服务端监听地址和端口必须可配置。
- 服务端不主动发送任何应用层数据，包括欢迎语、心跳、ACK 和错误响应。
- 服务端同时兼容“发送一帧后断开”和“保持连接并连续发送多帧”两种行为。
- 不依赖连接 IP 作为设备唯一身份；NAT 或移动网络可能导致 IP 变化。
- 可配置单连接空闲超时，但默认值必须大于设备最大上报周期；在上报周期未确认前建议关闭应用层空闲断开。
- 可以启用操作系统级 TCP keepalive 作为死连接清理手段，但它不属于业务心跳，也不会向设备发送应用报文；是否启用应由现场网络条件决定。

### 5.5 无 ACK 的可靠性边界

不发送 ACK 意味着设备无法确认服务端是否已经成功接收、落盘或写入 KH，因此端到端“绝不丢失”无法仅由服务端保证。服务端可保证的边界应定义为：

- 完整报文一旦被 Node.js 进程识别并成功持久化，后续到 KH 的写入采用可重试机制。
- 在报文到达前、连接中断、服务进程崩溃且尚未持久化等情况下，设备端如果不重传，服务端无法恢复该数据。
- 设备重复发送时，服务端应识别完全重复的报文，避免不必要的重复写入。

## 6 字段定义和解析规则

| 字段 | 示例 | 含义 | 建议解析类型 | 是否建议写 KH |
| --- | --- | --- | --- | --- |
| LEN | `0212` | 报文长度 | 整数 | 否，作为协议校验 |
| STC | `211000000800` | 站点号 | 字符串 | 作为设备/站点标识，可选写入 |
| SN | `0000000000` | 水表编号 | 字符串 | 作为设备标识，可选写入 |
| IMEI | `869098047062173` | 模组序列号 | 字符串 | 作为设备标识，通常不做趋势点 |
| CIMI | `460113126383366` | 查询模块序列号，原文如此命名 | 字符串 | 作为设备元数据，通常不做趋势点 |
| CCID | `89861120236017175088` | SIM 卡卡号 | 字符串 | 作为设备元数据，通常不做趋势点 |
| TM | `20210715153716` | 单值帧采集时间或批量帧第一条采集时间，格式 `yyyyMMddHHmmss` | 本地日期时间 | 作为首条数据的 `writeTime` |
| V | `3.60` | 电池电压 | 浮点数 | 是 |
| D | `030` | 批量历史数据相邻样本间隔，单位分钟 | 正整数 | 否，作为批量展开参数 |
| T | `08` | 批量字段包含的样本数量 | 正整数 | 否，作为批量展开参数 |
| C | `18` | 报文上传序号 | 整数或保留原字符串 | 建议用于追踪和去重 |
| A01 | `3.066` | 通道 01 模拟量 | 浮点数 | 是 |
| A02 | `3.652` | 通道 02 模拟量 | 浮点数 | 是 |
| A03 | `0.036` | 通道 03 模拟量 | 浮点数 | 是 |
| P01 | `000003663` | 脉冲通道 01 累计数 | 64 位整数 | 是 |
| P02 | `000000054` | 脉冲通道 02 累计数 | 64 位整数 | 是 |
| K01 | `00` | 开关量状态 | 布尔或整数 | 是，具体编码待确认 |
| 校验位 | `0B` | 报文校验值 | 两位十六进制 | 否，作为协议校验 |

### 6.1 必填字段建议

最小有效数据帧建议要求包含：

- `LEN`
- 至少一个稳定设备标识，优先级暂定为 `STC`、`SN`、`IMEI`
- `TM`
- 至少一个可写入的测量字段
- 校验位和帧尾 `#`

身份字段缺失、时间非法或没有测量字段的报文进入隔离区，不写入 KH。未知字段应保留在原始记录中并记录告警，但不应导致整帧失败，以便协议后续扩展。

### 6.2 时间处理

- `TM` 按 `yyyyMMddHHmmss` 严格解析，不允许自动纠正非法日期。
- 暂按现场所在时区解释，当前项目默认时区为 `Asia/Shanghai`。
- 调用 KH 时转换为 `yyyy-MM-dd HH:mm:ss.0`，例如 `2021-07-15 15:37:16.0`。
- 不使用服务器接收时间替代设备采集时间。
- 服务器接收时间另行保存，用于分析网络延迟和排障。
- 当测量字段使用 `|` 分隔时，第 `n` 个值的写入时间为 `TM + n × D` 分钟，且每个批量字段的值数量必须与 `T` 一致。
- 批量帧中的 V、V1、CSQ 等非数组字段只在 `TM` 写入一次，不复制到后续历史时刻。
- 允许的历史时间范围和未来时间偏差需要配置；超出范围的数据应隔离而不是静默改写时间。

### 6.3 数值处理

- 身份类字段必须按字符串保存，不能转为数字，否则会丢失前导零。
- `P01`、`P02` 虽然示例带前导零，但业务值应按 64 位非负整数解析；原文同时保留用于审计。
- `V`、`A01` 至 `A03` 使用十进制解析，不接受 `NaN`、`Infinity` 或包含非数字字符的值。
- `K01` 的 `00`、`01` 与开关状态对应关系必须由客户确认。
- `D`、`T` 已按现场样本确认分别为分钟间隔和样本数量；`C` 作为上传序号保留，循环规则仍需现场观察。

### 6.4 长度和校验

当前材料只说明 `LEN` 表示从帧头附近到校验位前分号的长度，但未给出是否包含 `@`、`LEN` 字段、末尾分号以及按字符数还是字节数计算。示例按常见口径直接计算时存在歧义，不能据此安全实现强校验。

当前材料也没有说明 `0B` 的算法、参与校验的字节范围、初始值、是否取反以及十六进制大小写规则。

因此实现应支持三种可配置策略：

- `off`：暂不校验，只解析并记录原值。
- `warn`：校验失败时记录告警但继续处理。
- `strict`：校验失败时进入隔离区，不写入 KH。

在厂商提供正式算法并用真实样本验证前，建议上线初期使用 `warn`，不建议自行猜测算法后直接丢弃数据。

### 6.5 可选通道发现

- `A01`～`A03`、`P01`～`P03` 按可选通道处理，不能假设每台设备或每一帧都包含全部通道。
- 解析器仅处理报文中实际出现的字段；缺失字段不得自动补 `0`。
- 首次发现的新通道进入“待确认点位”，由管理员配置业务名称、单位、倍率和 KH 点名后启用。
- 已启用通道偶发缺失时保留原有映射并记录追踪信息，不因单帧缺失删除点位。
- 当前样例只验证了 `P01`、`P02`，`P03` 属于客户口述支持范围，需用真实报文确认。

## 7 设备身份和 KH 点名映射

### 7.1 设备主键

建议建立独立的设备映射配置，不能依赖统一命名规则或点名前缀。配置至少包含：

| 配置项 | 用途 |
| --- | --- |
| deviceId | 系统内部设备唯一标识 |
| STC | 站点号匹配值 |
| SN | 水表编号匹配值 |
| IMEI | 模组标识辅助匹配 |
| enabled | 是否允许接入和写入 |
| fieldMappings | 报文字段到完整 KH 点名、类型、倍率和单位的显式映射 |

暂按 `STC` 识别站点，以 `SN`、`IMEI` 做一致性校验，但该规则属于待客户确认项。管理后台展示报文中的身份字段，不允许管理员随意切换系统唯一标识；若同一站点下存在多个水表，则可能需要改为 `STC + SN` 组合匹配。

### 7.2 KH 点位显式映射

现场 KH 变量名没有固定格式，因此不得通过 STC、字段名或统一前缀自动拼接目标点名。每台设备的每个启用字段必须显式绑定一个完整的 KH `tagName`。

管理后台通过 `khvariablesnumber` 和 `khvariables` 同步现有 KH 变量列表，管理员按名称或描述搜索并选择目标点位。映射配置至少包含：

| 配置项 | 说明 |
| --- | --- |
| deviceId | 系统内部设备标识 |
| sourceField | 报文字段，如 `A01` |
| businessName | 业务含义，如“瞬时流量” |
| khTagName | 完整 KH 变量名，不做自动拼接 |
| khTagType | 从 KH 变量列表读取的类型 |
| writeDataType | 调用 `khinsert` 时使用的数据类型 |
| scale、offset | 可选倍率和偏移量 |
| unit | 工程单位 |
| enabled | 是否写入 KH |

保存映射时必须校验：启用字段已选择目标点位、数据类型兼容、同一个 KH 点位未被多个启用字段重复绑定。未绑定字段不写入 KH，但保留在原始报文中。

### 7.3 建议的初始映射

| 报文字段 | KH 写入 dataType | KH 建点 tagType | dataQuality | dataVersion |
| --- | --- | --- | --- | --- |
| V、A01-A03 | 4，double | 10，FLOAT64 | 192 | 0 |
| P01、P02 | 2，int，需联调确认 64 位范围 | 8，INT64 | 192 | 0 |
| K01 | 1，bool，若业务定义为布尔 | 1，BOOLEAN | 192 | 0 |
| D、T、C | 2，int | 6 或 8，按范围选择 | 192 | 0 |
| STC、SN 等字符串 | 5，string | 11，NVARCHAR | 192 | 0 |

KH 文档中的“写数据 dataType”和“建点 tagType”是两套不同编号，代码中必须使用不同枚举，禁止复用同一个数字映射。

## 8 KH RESTful 集成需求

### 8.1 FDBServer 配置

- FDBServer 运行于 Windows 服务，连接 KH Server。
- KH Server IP、端口、用户名和 Base64 编码后的密码由 FDBServer 配置维护。
- FDBServer 的 HTTP/HTTPS 监听端口由部署环境提供。
- 生产环境优先使用 HTTPS；如果使用自签名证书，需要明确证书信任和续期方式。
- Node.js 服务不得把 KH 用户名、密码或 Authorization 值写入日志。

### 8.2 客户端注册

- 首次部署调用 `POST /api/v1/khregisterclient` 注册固定 `clientName`。
- 注册成功或返回“已注册”均视为可继续启动。
- `maxCount` 最大为 5，`minCount` 最小为 1；初始建议 `maxCount=4`、`minCount=1`，最终以现场 FDBServer 承载能力为准。
- 后续所有 KH 调用均携带 `Authorization: Base64(username:password)` 和 `clientName`。
- KH 文档没有展示 `Basic ` 前缀，联调时必须以实际 FDBServer 行为为准。

### 8.3 变量管理

可选方案如下：

1. 预建点：上线前由项目人员在 KH 中创建全部变量。风险最低，适合设备和字段固定的场景。
2. 自动建点：服务发现新设备或新字段后调用 `POST /api/v1/khaddtags`。自动化程度高，但需要严格控制命名、类型和权限。
3. 半自动：服务生成缺失点清单，人工确认后执行创建。推荐作为首期方案。

KH 文档说明变量列表缓存可能需要重启 FDBServer 才能看到新增变量，因此不能仅依赖变量列表接口立即验证建点结果。是否支持“建点后立即写值”必须联调确认。

### 8.4 数据写入

写入接口：

```text
POST /api/v1/khinsert
Content-Type: application/json
```

单条设备报文可转换为一个 `data` 数组，每个数组元素携带独立的 KH 点位和历史写入时间：

```json
{
  "data": [
    {
      "tagName": "北区_GPRS电压",
      "dataType": 4,
      "dataValue": 3.6,
      "writeTime": "2021-07-15 15:37:16.0",
      "dataQuality": 192,
      "dataVersion": 0
    },
    {
      "tagName": "流量计01_瞬时流量",
      "dataType": 4,
      "dataValue": 3.066,
      "writeTime": "2021-07-15 15:37:16.0",
      "dataQuality": 192,
      "dataVersion": 0
    }

```

批量大小、请求体最大值和接口并发数在文档中没有明确说明，必须通过现场版本联调确定，并做成可配置项。

### 8.5 返回值歧义

KH 文档对 `tag_oks` 的含义存在不一致：

- `khinsert` 示例旁的文字称其为“插入失败的变量名”。
- `khaddtags` 章节称其为“添加成功的变量集”。

程序不能仅凭字段名猜测结果，必须结合 `errorCode`、接口类型和真实联调响应分别实现。联调测试应覆盖全部成功、部分成功、全部失败、变量不存在、类型不匹配和重复数据。

## 9 可靠性设计

### 9.1 推荐处理流程

```text
TCP 收到完整帧
  -> 保存原始帧和接收元数据
  -> 协议校验与解析
  -> 保存标准化数据和待写任务
  -> TCP 接收流程结束，不返回数据
  -> 后台工作线程批量调用 KH
  -> 成功标记完成
  -> 失败先快速重试，超过阈值后转为低频持续重试
```

TCP 接收线程不得等待 KH 请求完成，否则 KH 变慢时会反向阻塞设备连接并放大数据丢失风险。

### 9.2 本地持久化队列

针对当前 30 台以上的规模，推荐首期使用 SQLite WAL 模式作为本地持久化队列，减少额外中间件部署。至少保存：

- 原始报文。
- 来源 IP、端口、连接标识和接收时间。
- 设备标识和解析结果。
- 报文状态：`received`、`parsed`、`pending`、`sending`、`retry`、`deferred`、`succeeded`。
- 重试次数、下次重试时间和最后一次错误。
- 去重键和内容哈希。
- KH 请求摘要及响应结果，敏感信息除外。

当容量或多实例需求增长时，可替换为 PostgreSQL、Redis Streams、RabbitMQ 或 Kafka，但不建议在当前规模下预先引入复杂中间件。

### 9.3 重试策略

- 网络错误、超时、HTTP 5xx、KH 临时不可用：指数退避并增加随机抖动。
- HTTP 401/403、clientName 未注册：停止快速重试并产生高优先级告警。
- 变量不存在：根据变量管理策略进入待建点或死信。
- 数据类型、点名或时间非法：不自动无限重试，直接进入死信。
- 部分点成功：仅重试明确失败的点，前提是联调能可靠识别部分失败结果。
- 服务重启后自动恢复所有未完成任务。

重试次数不作为最终丢弃条件。超过快速重试次数后转为 `deferred`，降低频率持续保留和重试；首次失败及转为低频重试时写入包含设备、帧、点位和批次标识的结构化日志。

### 9.4 去重和冲突

建议同时使用以下信息：

- 设备主键。
- `TM` 采集时间。
- `C` 上传序号。
- 规范化原始帧的 SHA-256 哈希。

完全相同的报文哈希在保留窗口内只生成一次 KH 任务。若设备、`TM` 和 `C` 相同但内容不同，应记录为数据冲突并保留两份原文，由明确的业务规则决定是否覆盖；不能静默选择其中一份。

## 10 异常处理

| 异常类型 | 示例 | 处理 |
| --- | --- | --- |
| 分帧异常 | 缺少 `@` 或 `#` | 丢弃无效前缀或保存未完成帧，不写 KH |
| 超长帧 | 持续接收但无 `#` | 达到上限后清理并告警 |
| 格式异常 | 字段无 `:`、字段重复 | 保存隔离记录，不写 KH |
| 身份异常 | STC/SN/IMEI 均无法映射 | 进入未知设备队列 |
| 时间异常 | 非法日期、超出允许窗口 | 进入隔离队列 |
| 数值异常 | A01 非数字 | 该字段失败；是否允许其余字段写入需配置 |
| 长度/校验失败 | LEN 或校验位不匹配 | 按 off/warn/strict 策略处理 |
| KH 鉴权失败 | 401/403 | 暂停写入并告警，保留队列 |
| KH 服务不可用 | 超时、连接失败、5xx | 异步重试 |
| KH 点不存在 | 变量未创建 | 待建点或死信 |
| 磁盘空间不足 | 队列无法落盘 | 停止接收新连接或立即告警，禁止静默丢弃 |

对于一帧中只有个别测量字段非法的情况，建议支持两种模式：

- 严格模式：整帧隔离，便于保证同一时间点数据完整性。
- 宽松模式：合法字段继续写入，非法字段进入死信。

首期建议使用严格模式，待客户确认业务容忍度后再调整。

## 11 安全需求

- 监听端口只对现场设备所在网络开放，使用防火墙白名单限制来源网段。
- 如果设备不能支持 TLS，公网传输必须通过专线、VPN 或隔离 APN，不能把明文 TCP 端口直接暴露到互联网。
- 设备身份字段只能用于识别，不等同于强认证；如需防伪造，应增加网络层隔离或设备签名能力。
- KH 凭据、Authorization、数据库文件和配置文件设置最小访问权限。
- 日志默认对 IMEI、CIMI、CCID 做脱敏，原始报文存储应限制访问并配置保留期限。
- 管理和健康检查接口不得与设备 TCP 端口复用。
- 依赖版本应锁定并具备离线安装包，适应现场网络受限环境。

## 12 可观测性和运维需求

### 12.1 日志

使用结构化日志，至少包含：

- connectionId、来源 IP、连接和断开时间。
- deviceId、STC、SN 的脱敏或业务允许形式。
- frameId、接收字节数、解析耗时和校验结果。
- 生成的 KH 点数、写入批次号、耗时和结果。
- 重试次数、错误分类和死信原因。

禁止在普通日志中记录 KH 密码、完整 Authorization 和未脱敏的 SIM 卡相关标识。

日志供管理后台按条件查询，本期不提供独立数据追踪页面、文件导出或批量下载能力。

### 12.2 指标

- 当前连接数、累计连接数、异常断开数。
- 接收帧数、有效帧数、异常帧数、重复帧数。
- 每秒接收帧数和字节数。
- 待写队列数量、最老待写数据年龄、死信数量。
- KH 请求成功率、失败率、延迟和重试次数。
- 按设备统计最后接收时间和最后成功写入时间。
- 磁盘使用率、进程内存、CPU 和事件循环延迟。

### 12.3 健康检查

- 存活检查：Node.js 进程和事件循环是否可工作。
- 就绪检查：TCP 监听是否成功、本地持久化是否可写。
- 下游检查：FDBServer 是否可访问、客户端是否已注册。
- 下游不可用时服务仍可接收并排队，因此不应把 KH 短时不可用等同于 TCP 服务不存活。

### 12.4 管理后台展示口径

- 前端定位为配置转发工具，只保留设备管理、转发配置和日志查询三个入口。
- 持久化队列、快速/低频重试、运行指标和数据链路追踪属于后端内部能力，不提供独立前端页面。
- 后端异常必须写入结构化日志，并保留 deviceId、frameId、KH 批次号和错误原因，供日志页面检索排障。
- 前端不展示 Worker、任务锁、并发槽、内部队列结构和处理时间线。

### 12.5 PM2 进程管理要求

- 生产环境统一使用 PM2 管理 Node.js 程序，不使用 Docker 作为本期部署前提。
- **PM2 必须随最终产品安装包一并交付**，不能要求现场服务器预先全局安装 PM2，也不能在安装时依赖互联网执行 `npm install -g pm2`。
- 交付包应包含经过测试并锁定版本的 PM2 运行文件及其依赖；部署和运维脚本必须调用包内 PM2，避免与服务器上可能存在的其他 PM2 版本冲突。
- 项目必须交付 `ecosystem.config.cjs`，统一定义应用名称、入口、工作目录、环境变量引用、日志路径和重启策略。
- 交付包必须提供统一的安装、启动、停止、重启、状态查询、日志查看和卸载脚本，现场人员无需直接拼写 PM2 命令。
- 正式交付包必须同时携带锁定版本的 Node.js Runtime、PM2 和全部生产依赖。现场服务器不需要预装 Node.js、npm、PM2，也不允许将联网下载依赖作为安装步骤。
- 应按最终目标操作系统和 CPU 架构制作对应的离线包；构建时生成依赖清单、版本信息和文件校验值，确保现场交付内容可追溯。
- 首期采用 `fork` 模式、`instances: 1`。约 300 台设备的 TCP 长连接不需要依靠 PM2 多实例扩容；单实例也可以避免 SQLite 多进程写竞争、重复消费和任务锁复杂化。
- 启用异常退出自动拉起、合理的重启延迟和连续异常保护，避免配置错误或外部依赖异常导致无限快速重启。
- PM2 只负责进程标准输出和标准错误；可供后台查询的业务日志仍由应用以结构化方式写入日志存储。
- PM2 日志必须配置轮转、单文件大小上限和保留期限，防止日志长期增长占满磁盘。
- 配置变更和版本升级应使用优雅停止。程序收到 `SIGINT`、`SIGTERM` 时停止接受新连接、完成当前落盘操作、释放数据库连接后退出；退出等待超过上限时才强制结束。
- 执行 `pm2 save` 保存当前进程清单，并根据最终操作系统配置开机自动恢复。Windows 环境应提供计划任务或经验证的 PM2 启动注册脚本，Linux 环境使用对应的 systemd 启动项。
- 不允许通过 PM2 cluster 模式直接启动多个共享同一 SQLite 队列的实例。未来若确需横向扩容，应先拆分 TCP 接入、队列和 KH Worker 的存储及任务所有权。

## 13 配置需求

建议配置项至少包括：

- TCP 监听 IP、端口、连接上限、最大帧长度和空闲超时。
- 编码、帧头、帧尾和字段分隔符。
- 长度与校验策略。
- 允许来源网段和设备白名单。

- KH 用户名、密码、clientName、连接池参数。
- KH 批量大小、重试策略和断路器参数。
- 本地数据库路径、保留期、归档和磁盘水位。
- 字段映射、倍率、单位、KH 点名和类型。

## 14 非功能需求建议

下列指标为基于“30 台以上设备”的首期建议基线，需结合真实上报频率确认：

| 类别 | 建议基线 |
| --- | --- |
| 并发连接 | 支持不少于 300 个并发设备连接 |
| 突发处理 | 支持 60 秒内每台设备连续补传 10 帧且不丢已落盘数据 |
| TCP 接收 | 不依赖 KH 响应时间；完整帧应快速落盘 |
| 可恢复性 | 进程异常重启后自动恢复待写任务 |
| 数据保留 | 成功数据摘要至少 30 天，失败和死信至少 90 天，最终由客户确认 |
| 时间精度 | 保留到秒，写入 KH 时补 `.0` |
| 可部署性 | 使用 PM2 管理进程，支持异常自动拉起、日志轮转、`pm2 save` 和开机自动恢复；最终操作系统待确认 |
| 可维护性 | 协议字段和 KH 映射可配置，不因增加 A04 等字段修改核心分帧代码 |

## 15 验收标准

### 15.1 TCP 和协议

1. 将一条合法报文拆成任意多个 TCP 数据片段发送，系统只解析出一条记录。
2. 一次发送两条及以上连续报文，系统逐条解析且无遗漏。
3. 报文前存在垃圾字节时，系统能恢复到下一个 `@`。
4. 缺少 `#` 的报文不会被误解析；超过限制后不会导致内存无限增长。
5. 同一连接可连续发送多帧，也可以每帧重新建连。
6. 服务端在所有正常和异常情况下均不向设备发送应用层心跳或 ACK。
7. 长度和校验策略可配置，严格模式能隔离错误帧。

### 15.2 字段和数据

1. 所有身份字段保留前导零。
2. `TM=20210715153716` 正确写为 `2021-07-15 15:37:16.0`。
3. V、A、P、K 等字段按确认后的类型和点名映射写入 KH。
4. 非法时间、非法数值、未知设备和未知字段均有明确记录，不静默丢弃。
5. 完全相同的重复帧只产生一次有效写入任务。

### 15.3 KH 集成

1. 服务能够完成 clientName 注册并在重启后识别已注册状态。
2. KH 正常时，合法报文可在约定时限内出现在 KS 历史趋势中。
3. KH 停止 1 小时期间，已接收数据保存在本地；KH 恢复后自动补写。
4. 写入部分失败时能够准确识别失败点并按确认规则处理。
5. 服务重启后未完成任务不丢失、不重复生成。
6. 变量不存在、类型不匹配、鉴权失败和证书错误均有可定位日志和告警。

### 15.4 运维

1. 服务由 PM2 以 `fork` 单实例模式管理，支持开机自动恢复和异常退出自动拉起。
2. 管理后台可维护设备、字段映射和 TCP/KH 转发配置，并按条件查询后台日志。
3. 日志中不包含 KH 密码或完整 Authorization。
4. 本地队列达到磁盘告警水位时能够告警并采取已定义的保护策略。
5. 管理后台不提供运行总览、告警中心、数据追踪、待写队列、导出或下载入口。
6. 连续运行测试期间，PM2 日志轮转有效，日志增长不会无限占用磁盘。
7. 人工结束 Node.js 子进程后，PM2 能自动恢复；重启后未完成的 SQLite 队列任务可继续处理。
8. 在未安装 Node.js、npm、PM2 且无法访问互联网的目标服务器上，使用交付包内 Runtime 和脚本仍可完成安装、启动、停止、重启、状态查询和开机自动恢复配置。

## 16 建议的模块划分

```text
src/
  tcp/              TCP 监听、连接管理、缓冲和分帧
  protocol/         LEN、校验、键值解析和字段校验
  devices/          设备识别、白名单和映射
  transform/        时间、类型、倍率和 KH 点值转换
  storage/          原始帧、任务、去重、死信和迁移
  kh/               注册、建点、写入、重试和响应解析
  workers/          异步批处理和恢复任务
  observability/    日志、指标和健康检查
  config/           配置加载、校验和密钥引用
  admin/            只读状态、补传和死信处理接口
tools/
  tcp-simulator/    半包、粘包、重复、异常和批量补传模拟器
```

TCP 接入、协议解析和 KH 写入必须解耦，便于用纯单元测试覆盖分帧逻辑，也便于未来增加其他下游而不影响设备接入。

## 17 实施阶段建议

### 阶段一 协议和 KH 联调验证

- 获取至少 20 条真实报文，覆盖不同设备、不同字段和值域。
- 确认 LEN 口径和校验算法。
- 确认设备连接生命周期、上报周期和补传行为。
- 使用现场 FDBServer 验证注册、建点、写入、部分失败及重复写入。
- 确认 KH 点名、类型、倍率、单位和时区。

### 阶段二 最小可用版本

- TCP 接入、分帧、解析和配置化映射。
- SQLite 持久化队列和 KH 异步写入。
- 基础重试、死信、日志、指标和健康检查。
- PM2 `ecosystem.config.cjs`、优雅退出和本地运行脚本。
- TCP 模拟器和自动化测试。

### 阶段三 现场试运行

- 先接入 1 至 3 台设备，连续运行并核对 KS 趋势。
- 扩展到全部设备，观察队列积压、KH 延迟和磁盘增长。
- 根据真实数据调整批量、并发、重试和保留期限。

### 阶段四 交付

- 包内 PM2 运行文件及依赖，不依赖现场全局安装或联网下载。
- 包内锁定版本的 Node.js Runtime 和全部生产依赖。
- PM2 部署脚本、`ecosystem.config.cjs`、开机自动恢复配置和日志轮转配置。
- 安装、启动、停止、重启、状态查询、日志查看和卸载脚本。
- 版本清单、第三方依赖清单和离线包文件校验值。
- 配置模板、字段映射表和设备清单。
- 运维手册、故障处理手册和数据补传流程。
- 测试报告、联调记录和验收报告。

## 18 待客户确认事项

### 18.1 阻塞开发的协议问题

1. `LEN:0212` 的准确计算范围是什么？是否包含 `@`、`LEN` 字段、校验前分号和中文所述端点？按字符数还是字节数？
2. `0B` 使用什么校验算法？参与计算的字节范围、初始值、取反规则和输出大小写是什么？
3. 设备一条 TCP 连接发送一帧后立即断开，还是保持长连接连续发送？两种情况是否都会出现？
4. 一台设备是否可能在一次连接中连续发送多条 `@...#` 原始帧？
5. 报文字段是否固定为当前这些字段？是否存在 A04、更多 P/K 通道或固件版本差异？

### 18.2 阻塞数据映射的问题

6. KH 点名已有规范和现成变量，还是由本工具创建？请提供设备清单和目标点名表。
7. 设备唯一身份应使用 STC、SN、IMEI，还是组合键？同一个 STC 下是否有多个 SN？
8. A01、A02、A03 分别代表什么物理量，单位、量程和倍率是什么？不同设备的通道配置是否可能不同？
9. P01、P02 是原始脉冲累计值，还是需要乘以脉冲当量后写入工程量？若需换算，请提供每台设备的系数和单位。
10. 是否所有型号都支持 P03？P03 在什么条件下出现，缺失字段表示通道未配置还是本次采集异常？
10. K01 中 `00`、`01` 及其他可能值分别代表什么状态？
11. D、T、C 是否需要写入 KH？C 是否会循环，循环范围是多少？
12. 设备时间 TM 使用哪个时区？设备时钟错误时是否仍写历史库？允许的最大未来/历史偏差是多少？

### 18.3 阻塞部署和验收的问题

13. Node.js 服务部署在 Windows 还是 Linux？是否与 FDBServer 同机？
14. 设备与服务器之间是局域网、专线/APN、VPN 还是公网？是否能配置防火墙白名单？
15. 真实上报周期、单次可能补传的最大帧数和设备最大数量是多少？
16. KH RESTful 的实际 IP、端口、HTTP/HTTPS、证书方式和测试账号何时可提供？
17. KH 暂停时本地最多需要保留多少天数据？可用磁盘空间是多少？
18. KS 中期望看到哪些趋势和报表，怎样判断数据转存验收通过？

## 19 当前建议决策

在以上问题全部确认前，可以先按以下非破坏性决策启动框架开发：

- 使用 `@` 和 `#` 分帧，支持半包、粘包和多帧。
- 服务端全程不向设备写任何应用数据。
- LEN 和校验先实现可插拔接口，默认 `warn` 模式。
- 原始报文先持久化，再异步写 KH。
- 使用 SQLite WAL 作为首期本地可靠队列。
- 使用配置化设备表和字段映射，不把点名规则写死。
- 将 KH 写数据类型和建点类型定义为两套独立枚举。
- 首期采用半自动建点，避免错误点名或错误类型污染生产 KH。
- 优先完成真实 FDBServer 的接口探测测试，再确定批量、并发和部分失败处理。
