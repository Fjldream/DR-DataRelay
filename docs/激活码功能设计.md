# Data Relay 激活码功能设计

## 1. 目标与范围

Data Relay 需要在完全离线的现场环境中完成软件授权，满足以下要求：

1. 内部授权人员可以使用独立的激活码生成工具签发授权。
2. 每张授权包含独立的最大设备数，例如 `300` 表示该激活码最多允许同时启用 300 台设备；300 不是系统固定值。
3. 授权与现场服务器机器码绑定，复制到其他服务器后不可使用。
4. 客户可在管理后台查看机器码、导入激活码和查看授权状态。
5. 授权校验不得显著影响 TCP 接入和 KH 转存性能。
6. 客户不能通过修改激活码内容、数据库配置或前端参数提高授权数量。

本期将用户口述的“点位限制”定义为“设备授权数”。设备授权数完全由当前激活码的 `maxDevices` 决定，可以按合同签发 50、300、500 等不同规格，不在程序中写死。设备内部的 A01、P01 等 KH 字段映射不单独计数。数据结构预留 `maxKhMappings` 字段，后续如需按 KH 点位数授权，可独立启用，不改变现有激活码格式。

## 2. 总体方案

采用 Ed25519 非对称数字签名：

- 激活码生成工具持有私钥，用于签发授权。
- Data Relay 交付程序只内置公钥，用于验证授权。
- 私钥不进入源代码仓库、不放入客户交付包，也不发送到现场。
- 激活码中的客户名称、机器码和授权数量可以读取，但任何修改都会使签名失效。
- 全流程不需要互联网、授权服务器或第三方服务。

激活码格式：

```text
DRL1.<Base64URL(payload JSON)>.<Base64URL(Ed25519 signature)>
```

同时支持两种交付方式：

- 复制粘贴激活码文本。
- 导入 UTF-8 编码的 `.lic` 授权文件。

两者内容完全相同。激活码较长时优先使用授权文件，避免人工复制出错。

## 3. 授权数据结构

授权载荷使用字段顺序固定的规范 JSON，示例：

```json
{
  "schemaVersion": 1,
  "licenseId": "LIC-20260929-0001",
  "product": "data-relay",
  "customer": "示例客户",
  "project": "某现场数据转存项目",
  "machineCode": "DRM-4A92-78F1-0B6C-...",
  "maxDevices": 300,
  "maxKhMappings": null,
  "issuedAt": "2026-09-29T00:00:00.000Z",
  "notBefore": "2026-10-01T00:00:00.000Z",
  "expiresAt": "2027-10-01T00:00:00.000Z",
  "keyId": "prod-2026-01",
  "nonce": "随机 128 位值"
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `schemaVersion` | 授权格式版本，首版为 1 |
| `licenseId` | 唯一授权编号，用于内部追溯 |
| `product` | 固定为 `data-relay`，防止跨产品使用 |
| `customer` | 客户名称 |
| `project` | 项目或现场名称 |
| `machineCode` | 目标服务器机器码 |
| `maxDevices` | 最大同时启用设备数，必须为正整数 |
| `maxKhMappings` | 预留的 KH 映射数量限制，首版为 `null` |
| `issuedAt` | 签发时间 |
| `notBefore` | 必填，授权开始时间，使用 UTC ISO 8601 时间 |
| `expiresAt` | 必填，授权到期时间，必须晚于开始时间 |
| `keyId` | 签名密钥编号，支持后续公钥轮换 |
| `nonce` | 防止相同参数产生完全相同的授权码 |

所有正式授权必须包含有效期，不允许签发永久授权。授权工具可以提供 1 个月、3 个月、6 个月、1 年等快捷期限，也允许输入明确的到期日期。生成器根据所选现场时区将生效和到期时间转换成 UTC 后签名，服务端展示时再转换为现场时区。

## 4. 机器码设计

### 4.1 原始机器标识

根据操作系统读取稳定的系统标识：

| 系统 | 首选标识 | 备用标识 |
| --- | --- | --- |
| Windows | 注册表 `MachineGuid` | 系统盘卷序列号 |
| Linux | `/etc/machine-id` | DMI `product_uuid` |
| macOS | `IOPlatformUUID` | 系统硬件 UUID |

不使用 IP、MAC 地址、主机名或 TCP 端口作为机器码来源，因为这些值在现场容易变化。

### 4.2 生成规则

1. 读取并规范化原始标识：去除首尾空格并转换为大写。
2. 计算 `SHA-256("data-relay-machine-v1|" + os + "|" + rawId)`。
3. 将摘要编码为大写 Base32，并以便于人工核对的分组形式展示。
4. 管理后台和生成工具只传递处理后的机器码，不泄露原始系统标识。

示例：

```text
DRM-4A92-78F1-0B6C-6C31-83AF-019D-7D02-9A11
```

### 4.3 稳定性与换机

- 普通重启、IP 变化、网卡更换和应用升级不应改变机器码。
- 重装操作系统、克隆虚拟机、主板更换或系统 Machine ID 重置可能改变机器码。
- 机器码改变后原授权失效，但设备配置、SQLite 数据和日志不得被删除。
- 换机时由内部授权人员对新机器码重新签发授权，旧授权的撤销在内部签发记录中留痕。
- 完全离线授权无法在到期时间之前实时撤销，这是离线授权的固有限制；如必须立即撤销，需要缩短授权周期或引入联网授权服务。

## 5. 激活码生成工具

生成工具是独立的内部工具，不放入客户交付包。

### 5.1 输入项

- 客户名称，必填。
- 项目或现场名称，必填。
- 现场机器码，必填并校验格式。
- 最大设备数，必填，正整数，例如 300。
- 生效时间，必填，默认当前时间。
- 到期时间，必填，必须晚于生效时间。
- 备注，仅存内部签发记录，不写入公开载荷。

### 5.2 输出项

- 激活码文本。
- `<licenseId>.lic` 授权文件。
- 授权摘要：客户、项目、机器码尾段、最大设备数、生效时间、到期时间和签发时间。
- 内部签发记录，不保存客户 KH 密码或其他业务密钥。

### 5.3 工具形态

首版实现为 Node.js 命令行工具，并提供 Windows `.cmd` 启动入口；后续可在相同签名核心之上增加本地桌面表单。建议命令：

```text
license-generator generate \
  --customer "客户名称" \
  --project "项目名称" \
  --machine-code "DRM-..." \
  --max-devices 300 \
  --valid-from "2026-10-01" \
  --valid-until "2027-10-01" \
  --timezone "Asia/Shanghai" \
  --output ./licenses
```

私钥使用加密的 PKCS#8 文件保存，运行生成器时输入口令解密。生成器应拒绝使用权限过宽的私钥文件，并将每次签发追加到内部 SQLite 台账。

## 6. 服务端授权模块

新增 `LicenseManager`，职责如下：

1. 计算本机机器码。
2. 读取 `data/license.lic`。
3. 根据 `keyId` 选择内置公钥。
4. 验证激活码格式、Ed25519 签名、产品名、机器码、生效时间和到期时间。
5. 将结果缓存为只读授权状态。
6. 在授权文件发生变化时重新验证。
7. 向设备管理和 TCP 接入提供轻量级授权判断。

签名验证只在以下时机执行：

- 程序启动时。
- 管理员导入新激活码时。
- 授权文件发生变化时。
- 可选的低频完整性检查，例如每 5 分钟一次。

每条设备报文只查询内存缓存、当前时间和允许设备集合，不执行签名或硬件信息读取，因此不会明显影响 300 台以上设备的 TCP 性能。服务端在授权到期时间点立即将缓存状态切换为过期，不依赖重启或人工刷新。

## 7. 设备数量限制

### 7.1 计数口径

- `maxDevices` 取自当前有效激活码，不使用固定默认值；例如 `maxDevices=300` 表示数据库中最多有 300 台 `enabled=true` 的设备。
- 自动发现但尚未配置的设备为 `enabled=false`，不占用授权数量。
- 停用设备后释放一个授权名额。
- 字段映射数量不占设备授权名额。
- 同一 STC 对应同一设备，不因重复连接或重复报文重复计数。

### 7.2 后端强制校验

限制必须由后端执行，不能只依赖前端：

1. 新增或编辑设备并准备将其启用时，在 SQLite 事务内统计已启用设备数。
2. 达到授权上限时拒绝保存，返回 HTTP `409 LICENSE_DEVICE_LIMIT_REACHED`。
3. 启动时根据稳定顺序构建允许设备集合；如果数据库被人工修改导致超限，只允许最早启用的授权数量，超出设备不生成 KH 任务并记录错误日志。
4. TCP 收报路径再次检查当前设备是否位于允许集合，防止绕过管理接口直接修改数据库。
5. 授权数量降低时不删除设备、映射和历史数据，超出部分自动停写并提示管理员处理。

建议为设备增加 `enabled_at` 字段，允许设备集合按 `enabled_at ASC, id ASC` 稳定计算，避免每次重启选择不同设备。

### 7.3 并发安全

两名操作或两个请求同时启用设备时，数量统计与更新必须在同一写事务中执行，确保不会出现 299 台同时提交两次后变成 301 台的情况。

## 8. 未激活和授权异常行为

未激活、签名错误、机器码不匹配或授权过期时：

- 管理后台仍可登录。
- 授权页面、机器码、系统日志和已有设备配置仍可查看。
- 不删除 SQLite 数据、设备配置、点位映射和日志。
- TCP 端口继续监听并保存原始报文。已有的启用设备继续生成状态为 `license_hold` 的 KH 任务；任务只积压、不发送。有效期已过的授权按原设备上限生成，完全未激活时只针对升级前已经启用的设备生成。
- KH Worker 暂停发送待写任务，避免在未授权状态下继续转存。
- 健康检查仍返回进程存活；就绪状态增加 `licenseValid=false`，便于运维识别。
- 后台持续显示醒目的授权异常状态，业务日志记录具体错误码，但不记录完整激活码。

选择“继续接收并保存原始报文”是为了防止授权误操作造成现场原始数据丢失。若商务规则要求未激活时完全拒绝 TCP，可改为关闭 TCP 监听，但不建议作为默认策略。

## 9. 管理后台设计

左侧导航增加“软件授权”，但不增加角色权限体系。

页面展示：

- 授权状态：未激活、尚未生效、有效、即将到期、已过期、机器不匹配、签名无效、系统时钟异常。
- 本机机器码及“复制机器码”按钮。
- 客户名称、项目名称和授权编号。
- 设备用量，例如 `126 / 300`。
- 签发时间、生效时间、到期时间和剩余天数。
- 粘贴激活码输入框和 `.lic` 文件导入按钮。
- “验证并激活”按钮。

设备页面同步显示紧凑的授权用量。在达到上限时，启用开关不可提交，并根据当前激活码动态提示，例如“当前授权最多启用 300 台设备”。

不得在前端显示完整激活码、签名、公钥内容或原始机器标识。

## 10. API 设计

### `GET /api/license`

返回脱敏后的授权状态：

```json
{
  "status": "valid",
  "machineCode": "DRM-...",
  "licenseId": "LIC-20260929-0001",
  "customer": "示例客户",
  "project": "某现场数据转存项目",
  "maxDevices": 300,
  "enabledDevices": 126,
  "notBefore": "2026-10-01T00:00:00.000Z",
  "expiresAt": "2027-10-01T00:00:00.000Z",
  "remainingDays": 365
}
```

### `POST /api/license/activate`

请求：

```json
{ "activationCode": "DRL1...." }
```

处理顺序为：解析、签名验证、产品验证、机器码验证、有效期验证、原子写入临时文件、重命名为 `data/license.lic`、刷新授权缓存。

### 错误码

| 错误码 | 含义 |
| --- | --- |
| `LICENSE_REQUIRED` | 尚未激活 |
| `LICENSE_FORMAT_INVALID` | 激活码格式错误 |
| `LICENSE_SIGNATURE_INVALID` | 签名验证失败 |
| `LICENSE_MACHINE_MISMATCH` | 激活码不属于本机 |
| `LICENSE_NOT_YET_VALID` | 尚未到生效时间 |
| `LICENSE_EXPIRED` | 授权已过期 |
| `LICENSE_CLOCK_ROLLBACK` | 检测到系统时间明显回退 |
| `LICENSE_DEVICE_LIMIT_REACHED` | 已达到设备授权上限 |
| `LICENSE_KEY_UNKNOWN` | 当前程序不认识签名密钥编号 |

## 11. 存储与日志

- 授权文件保存到 `data/license.lic`，随数据目录持久化。
- SQLite 保存授权摘要和激活操作日志，但不保存生成器私钥。
- 业务日志记录激活成功、验证失败、机器码变化、即将到期、过期和设备超限。
- 日志只记录 `licenseId` 和机器码尾段，不记录完整激活码。
- 离线备份可以包含授权文件，但恢复到另一台机器后会因机器码不同而失效。

### 11.1 到期提醒与续期

- 距到期 30 天、7 天和 1 天时，在管理后台持续显示提醒，并分别写入一次业务日志。
- 到期后继续接收并保存原始报文；原授权范围内的设备继续生成 `license_hold` 任务，但 KH Worker 不发送这些任务。
- 已有设备、映射、原始报文、待写任务和日志均不得删除。
- 续期时为同一机器码重新签发激活码；新授权可同时修改 `maxDevices`。
- 新授权验证成功后原子替换旧授权，将仍在新授权设备范围内的 `license_hold` 任务批量恢复为 `pending`，再恢复 KH Worker，因此到期期间的数据可以自动补写。
- 首次激活前或激活码完全无效期间，升级前已经启用的设备生成 `license_hold` 任务；新发现设备仍保持未启用，不生成任务。激活后仅释放当前授权设备范围内的暂停任务。
- 如果续期授权降低了 `maxDevices`，超出新上限设备的 `license_hold` 任务继续保留但不发送，直到设备被纳入有效授权范围或由管理员明确处理。

### 11.2 系统时间回退

有效期授权依赖现场服务器时间。服务端每隔固定周期持久化“已见到的最大系统时间”；如果当前时间比该值回退超过 10 分钟，则将授权置为 `LICENSE_CLOCK_ROLLBACK` 并暂停 KH 转存，待管理员修正系统时间后自动恢复。

完全离线且客户拥有服务器管理员权限时，软件无法从密码学上绝对阻止系统时间和本地状态被同时篡改。若未来要求强防时间篡改，需要使用 TPM、安全硬件或周期性连接授权服务器。本期采用时间回退检测、日志留痕和签名授权的组合方案。

## 12. 密钥管理与构建要求

1. 使用独立脚本一次性生成 Ed25519 密钥对。
2. 私钥只保存在内部受控设备或加密介质中，并准备受控备份。
3. 公钥以 `keyId -> publicKey` 的只读映射编译进 Data Relay。
4. 正式私钥不得出现在 Git、npm 包、离线交付包、构建日志或测试夹具中。
5. 测试使用单独的测试密钥对，不得用正式私钥跑自动化测试。
6. 密钥轮换时新增公钥，不立即删除旧公钥，以保证尚未到期的旧授权继续可用。

## 13. 测试与验收

### 自动化测试

- 正确机器码和签名验证成功。
- 任意修改 `maxDevices` 后验证失败。
- 复制授权到另一机器码后验证失败。
- 未知 `keyId`、格式损坏、尚未生效、已过期和系统时间明显回退均返回正确错误码。
- 第 300 台设备可以启用，第 301 台被拒绝。
- 停用一台后可再启用一台。
- 并发启用不会突破授权上限。
- 人工修改 SQLite 为超限后，运行时仍只允许授权数量的设备写入。
- 未激活时原始报文继续落盘；授权过期时生成 `license_hold` 任务但不发送。
- 续期后 `license_hold` 任务恢复为 `pending` 并自动补写，且不会生成重复任务。
- 距到期 30 天、7 天、1 天时正确显示提醒且每个阈值只记录一次日志。
- 同一机器续期后恢复 KH 转存，并按新激活码更新设备上限。
- 重启后授权、设备用量和待写任务保持一致。

### 现场验收

1. 在目标服务器后台复制机器码。
2. 使用内部生成器签发 300 台、具有明确到期时间的测试授权。
3. 导入激活码并核对客户、项目、机器码和设备数。
4. 启用测试设备并确认 KH 转存正常。
5. 在另一台服务器导入相同激活码，确认机器码不匹配。
6. 使用测试授权验证达到上限后的提示和日志。
7. 导入短期测试授权，验证到期后暂停 KH 转存以及续期后的恢复行为。

## 14. 实施拆分

建议按以下顺序开发：

1. 机器码模块和跨平台测试。
2. 测试密钥、签名格式和 `LicenseManager`。
3. 独立的内部激活码生成工具。
4. 授权文件原子导入和授权 API。
5. 设备启用事务及 TCP/KH Worker 双重限制。
6. 管理后台授权页面和设备用量提示。
7. PM2 重启恢复、离线包构建和跨平台验收。
